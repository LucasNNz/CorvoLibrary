2. FAST CONTROL PLANE
======================================================================

2.1 Contadores materializados e state_version

A tabela automatic_projects passa a manter:
- total_items;
- approved_count;
- frozen_count;
- collecting_count;
- materializing_count;
- waiting_qa_count;
- relink_count;
- technical_count;
- waiting_seed_count;
- failed_count;
- pending_count;
- state_version;
- last_frozen_at.

As mutações relevantes atualizam o resumo/versionamento. Leituras simples não precisam remontar o projeto inteiro a partir de todos os itens.

2.2 Leituras compactas

- obter_projeto_automatico usa getAutomaticProjectSummary().
- listar_projetos_automaticos usa listAutomaticProjectsFast().
- obter_detalhes_projeto_automatico fica disponível quando o payload completo é realmente necessário.
- obter_estado_supervisor deixa de reconciliar implicitamente o projeto.
- R2 não é consultado para montar o resumo operacional.

2.3 Paginação por cursor

A listagem rápida de projetos usa cursor estável `updated_at|id`, evitando OFFSET crescente.

2.4 Snapshot operacional + delta sync

Novo MCP:
- obter_snapshot_operacional(projeto_id, since_version, limite_pacote)

Retorna em uma chamada:
- project version;
- counts;
- next_actions;
- até 20 QA;
- até 20 relinks;
- até 20 correções técnicas;
- decisões relevantes;
- workers;
- throughput;
- detector de pipeline travado.

Se since_version já for a versão atual:
- changed=false;
- não devolve novamente o estado pesado.

2.5 Operações compostas / write + return state

Novos fluxos em lote:
- aplicar_decisoes_supervisor_lote;
- relinkar_itens_lote;
- materializar_urls_lote.

A aplicação de decisões do Supervisor retorna persistência + versão + contadores + snapshot, evitando WRITE → GET → GET para confirmação/próximo passo.

2.6 Idempotência e recuperação após timeout

Foi criada a tabela operation_results.

Mutações compostas aceitam operation_id e persistem:
- RUNNING;
- COMPLETED;
- FAILED;
- resultado;
- erro;
- timestamps.

Novo MCP:
- obter_resultado_operacao(operation_id).

Assim, timeout do cliente não obriga a repetir trabalho já persistido.

======================================================================
5. PARALLEL DATA PLANE
======================================================================

5.1 SKIP WAITING

O loop de projeto trata QA/relink/correção/waiting seed como bloqueio do ITEM, não do PROJETO.

Estados de espera liberam o fluxo para os demais itens.

5.2 Coleta larga

executeCollection() trabalha múltiplos termos em paralelo:
- padrão: 10 termos;
- configurável até 20;
- Promise.allSettled;
- falha de um termo é isolada e não encerra os demais.

5.3 Materialização paralela

- concorrência global existente permanece 8;
- limite por host permanece controlado;
- configuração legada `collection_parallelism=3` é elevada para 8 somente quando ainda está no default antigo;
- tuning explícito diferente de 3 é preservado.

5.4 QA em lote

O fluxo de QA faz prefetch em lote de itens/materializações e registra decisões por lote, removendo o padrão N+1 mais caro.

5.5 Relink em lote

Novo MCP relinkar_itens_lote trabalha até 20 itens numa única interação do Supervisor.

5.6 Materialização em lote

Novo MCP materializar_urls_lote trabalha até 20 itens e usa operation_id para idempotência.

6. INFRAESTRUTURA ÓBVIA NÃO VAI PARA O SUPERVISOR
======================================================================

A fila do Supervisor filtra ocorrências óbvias como:
- HTTP_404;
- HTTP_403;
- SOURCE_EMPTY;
- SOURCE_NOT_CONFIGURED;
- BRAVE_DISCOVERY_NAO_CONFIGURADO;
- DOWNLOAD_TIMEOUT;
- RATE_LIMITED.

SOURCE_NOT_CONFIGURED também desativa automaticamente a fonte de coleta correspondente, impedindo que a mesma falta de configuração consuma rodadas repetidas até ser reabilitada/configurada.

======================================================================
8. CIRCUIT BREAKER ADAPTATIVO
======================================================================

A V56 deixa de tratar duas URLs ruins como razão automática para derrubar um host historicamente saudável.

O threshold considera o histórico do host. Hosts com histórico >=20 sucessos e taxa >=80% exigem mais falhas recentes antes de abrir o breaker global. A URL ruim continua podendo ser descartada sem punir todo o domínio.

======================================================================
9. PIPELINE STALLED DETECTOR
======================================================================

O snapshot operacional marca pipeline_stalled quando:
- há mais de 20 pendências;
- não há novo progresso/congelamento por 10 minutos;
- existe trabalho READY;
- existe capacidade disponível.

Diagnósticos possíveis:
- QA_CONGESTIONADO;
- RELINK_CONGESTIONADO;
- CIRCUIT_BREAKER_ATIVO;
- SUPERVISOR_PENDENTE;
- CAPACIDADE_DISPONIVEL_COM_FILA;
- MATERIALIZADOR_SEM_WORKER.
