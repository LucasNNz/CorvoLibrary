======================================================================
1. OBJETIVO
======================================================================

Transformar a operação do Supervisor IA de um modelo baseado em microchamadas MCP
para um modelo industrial baseado em ORDENS OPERACIONAIS DE ALTO NÍVEL.

A regra principal passa a ser:

1 CHAMADA DO SUPERVISOR
→ CRIA 1 PLANO OPERACIONAL
→ O APP RAMIFICA EM N AÇÕES INTERNAS
→ WORKERS EXECUTAM EM PARALELO
→ RESULTADOS CONVERGEM
→ O APP CONTINUA SOZINHO
→ O SUPERVISOR SÓ VOLTA A SER ACIONADO EM DIVERGÊNCIA REAL.

O Supervisor não deve mais operar a Biblioteca ferramenta por ferramenta.

O Supervisor deve:

- enxergar;
- decidir;
- definir intenção;
- definir política;
- distribuir trabalho;
- resolver exceções;
- aprovar/rejeitar em lote;
- mudar estratégia quando necessário.

O APP deve:

- executar imediatamente;
- fan-out;
- distribuir tarefas;
- controlar leases;
- enfileirar;
- coletar;
- materializar;
- testar;
- corrigir tecnicamente;
- relinkar quando permitido;
- congelar;
- atualizar estado;
- persistir resultados;
- continuar até o próximo decision boundary.

======================================================================
2. REGRA DE OURO
======================================================================

A IA NÃO DEVE CONDUZIR O PIPELINE PASSO A PASSO.

Fluxo errado:

consultar
→ interpretar
→ rejeitar 1
→ esperar
→ confirmar
→ obter estado
→ continuar
→ esperar
→ listar próxima candidata
→ interpretar
→ repetir.

Fluxo correto:

Supervisor recebe pacote
→ decide várias coisas
→ envia 1 plano
→ app confirma imediatamente
→ app distribui dezenas de ações
→ workers continuam em paralelo
→ app só volta quando existir nova divergência real ou novo pacote relevante.

REGRA:

"CADA INTERAÇÃO DO SUPERVISOR DEVE MAXIMIZAR O TRABALHO ÚTIL
DESENCADEADO POR ROUND TRIP."

3. MODELO OPERACIONAL INDUSTRIAL
======================================================================

O Supervisor deixa de agir como operador de máquina.

- controle de qualidade;

- planejador de rotas;

A Biblioteca passa a agir como:

- executor;
- memória operacional;
- controlador de workers;
- motor de fan-out/fan-in;
- sistema de recuperação;
- observabilidade.

======================================================================
4. CONCEITO CENTRAL — EXECUTAR ATÉ DIVERGÊNCIA
======================================================================

Criar um modo operacional:

EXECUTAR_ATÉ_DIVERGÊNCIA

Quando o Supervisor autoriza a execução de um projeto, etapa ou lote:

o APP continua automaticamente até que uma das condições abaixo aconteça:

1. exista ambiguidade visual real;
2. exista conflito semântico;
3. nenhuma rota automática permitida resolva o item;
4. nenhuma candidata tecnicamente válida exista;
5. haja conflito de regra;
6. uma decisão de referência precise do Supervisor;
7. um limite operacional seja atingido;
8. o projeto/lote termine;
9. um pacote de decisão alcance o tamanho mínimo configurado;
10. aconteça uma exceção real.

Nenhum outro evento deve parar o pipeline.

DECISION_BOUNDARY deve ser criado apenas quando o APP realmente não puder

Casos que NÃO devem criar decision boundary:

timeout isolado

próxima candidata disponível
retry permitido

fila temporariamente vazia
relink automático de primeiro nível permitido.

======================================================================
8. FAN-OUT
======================================================================

Uma única decisão do Supervisor deve poder gerar múltiplas ações internas.

Exemplo:

Supervisor rejeita 005-naruto.png e autoriza:

- tentar próxima candidata;
- abrir até 3 queries;
- usar 3 fontes;
- materializar até 4 arquivos;
- parar quando houver 2 candidatas tecnicamente válidas;
- bloquear Openverse para este target;
- manter Wikia/Zerochan como preferenciais;
- relinkar somente se todas as alternativas falharem.

Uma única decisão pode gerar:

3 queries
× 3 fontes
→ várias URLs
→ 4 materializações selecionadas
→ precheck
→ 2 candidatas válidas

Tudo isso sem nova chamada MCP.

======================================================================
9. FAN-IN
======================================================================

Após as ramificações:

os resultados devem convergir para um agregador.

Criar:

PLAN_AGGREGATOR

ou lógica equivalente.

Ele deve decidir:

SE a tarefa foi resolvida automaticamente
→ continuar pipeline.

SE há candidatas prontas para QA
→ enfileirar QA.

SE todas as rotas falharam
→ abrir RELINK ou decision boundary.

SE o item foi aprovado
→ congelar.

SE existem alternativas suficientes
→ não chamar Supervisor ainda.

SE o pacote de divergências atingiu o tamanho configurado
→ gerar WORK_PACKET.

======================================================================
11. SUPERVISOR EXCHANGE
======================================================================

Criar uma ferramenta central:

supervisor_exchange

Essa deve se tornar a ferramenta principal do caminho quente.

Entrada:

project_id
execution_id opcional
previous_work_packet_id opcional
decisions[]
policies[]
commands[]
operation_id
idempotency_key

Ela deve fazer:

1. validar lease;
2. adquirir/renovar lease se apropriado;
3. aplicar decisões do pacote anterior;
4. persistir tudo atomicamente ou de forma idempotente;
5. criar SUPERVISOR_PLAN;
6. fan-out das ações internas;
7. atualizar filas;
8. liberar workers;
9. atualizar contadores;
10. incrementar state_version;
11. retornar ACK imediato;
12. opcionalmente retornar próximo pacote já pronto se existir.

Retorno rápido:

accepted
operation_id
plan_id
project_version
branches_created
workers_dispatched
counts
next_work_packet
next_supervisor_action

======================================================================
12. ACK IMEDIATO
======================================================================

Toda chamada de plano deve responder rápido.

Meta:

- validação;
- persistência;
- criação do plano;
- criação das unidades;
- retorno.

Não esperar:

- downloads;
- buscas externas;
- ZIP;
- dezenas de materializações;
- relink completo;
- pipeline inteiro;
- decisões futuras.

Exemplo:

accepted=true
plan_id=PLAN-ABC
branches_created=47
workers_dispatched=8
project_version=231
next_supervisor_action=NONE

O APP continua depois do ACK.

======================================================================
13. EXECUÇÃO ASSÍNCRONA DO APP
======================================================================

Após o ACK:

workers consomem PLAN_BRANCH.

O APP continua independentemente da conversa.

O ChatGPT não deve ficar esperando uma conexão longa.

Toda operação longa deve ser:

job persistido
→ execução no backend
→ status persistido
→ resultado recuperável.

======================================================================
14. SUPERVISOR PODE CONTINUAR VISIONANDO
======================================================================

Objetivo operacional:

enquanto o APP executa o plano A,
o Supervisor pode estar:

- analisando pacote B;
- vendo 20 imagens;
- decidindo QA;
- preparando relinks;
- ajustando política;
- distribuindo trabalho de outro projeto.

A IA não deve ficar bloqueada esperando a execução física das ações.

18. BUFFER DE CANDIDATAS
======================================================================

Não trabalhar com apenas uma candidata por vez.

Para cada item:

TARGET BUFFER desejado:
2–3 candidatas boas prontas.

Teto normal:
5 materializadas.

Fluxo:

coleta
→ materializa alternativas
→ precheck
→ buffer
→ QA.

Se a primeira for rejeitada:

não voltar imediatamente à internet.

PROMOVER próxima candidata.

Somente voltar à descoberta quando o buffer ficar abaixo do mínimo.

19. PRECHECK SEMÂNTICO FORTE
======================================================================

Antes de entregar candidata para QA visual:

validar:

project_domain
universe
target
canonical_reference
required_entities
forbidden_entities
composition_class
slot
preset
source compatibility

filename/context metadata
duplicate similarity

Exemplo:

target = Naruto
required_entity = Naruto Uzumaki
forbidden_conflict = Sasuke-only

Se metadados/rota indicarem claramente Sasuke sem Naruto:

descartar antes do QA.

IMPORTANTE:

precheck não substitui QA visual.

Ele apenas elimina erros óbvios.

======================================================================
20. RELINK AUTOMÁTICO EM CAMADAS
======================================================================

RELINK deve ter níveis.

NÍVEL 0
próxima candidata já pronta.

NÍVEL 1
nova URL da mesma referência.

NÍVEL 2
nova fonte da mesma referência.

NÍVEL 3
variação de query da referência canônica.

NÍVEL 4
alternativa semântica previamente autorizada.

NÍVEL 5
decision boundary → Supervisor.

O Supervisor não deve ser chamado nos níveis 0–3 quando houver política válida.

======================================================================

- criar branches;

- relink permitido;

- correção técnica permitida;
- atualização de prioridade;
- atualização de política operacional;
- snapshot;

Essas operações devem ser:

REGRA:

======================================================================
24. WRITE + RETURN STATE
======================================================================

Toda mutação composta deve retornar estado suficiente.

Não fazer:

WRITE
→ GET confirmação
→ GET estado
→ GET próximo trabalho.

Fazer:

WRITE
→ retorno confirma persistência
→ retorno traz project_version
→ retorno traz counts
→ retorno traz next_work_packet se disponível.

======================================================================
25. LEASE
======================================================================

Lease deve continuar granular.

SUPERVISOR lease:
coordena a sessão.

WORKER lease:
protege unidade de trabalho.

PLAN_BRANCH lease:
protege ramificação.

Uma execução antiga não pode alterar branch reassigned.

Aquisição de lease do Supervisor deve continuar muito curta.

Não fazer backfill/reconcile completo no hot path da aquisição.

======================================================================
26. DISTRIBUIÇÃO DE WORKERS
======================================================================

Após criação do plano:

branches devem entrar imediatamente nas filas adequadas.

COLLECTOR
MATERIALIZER
PRECHECK
ANALYST
RELINK
TECHNICAL_FIX
FREEZE
ORGANIZER
EXPORTER

Cada worker:

assume próxima unidade
→ executa
→ persiste
→ libera
→ próxima.

Nenhum worker deve esperar o Supervisor quando há trabalho determinístico disponível.

======================================================================
27. BACKPRESSURE
======================================================================

Não deixar uma etapa produzir backlog ilimitado.

Exemplo:

QA backlog > threshold
→ reduzir materializações novas daquele tipo
→ manter discovery útil
→ priorizar conclusão de buffers
→ aumentar prioridade de QA
→ evitar milhares de arquivos desnecessários.

Configurações:

max_wip_by_stage
max_qa_backlog
max_relink_backlog
max_materialized_buffer
max_project_wip

APÊNDICE V60-A — DIAGNÓSTICO OPERACIONAL BS18 / GATE DE ROTEAMENTO
======================================================================

O teste da Biblioteca Semântica 18 confirmou que controle/estado, paralelismo,
relink em lote e rejeitar/continuar evoluíram, mas mostrou dois gargalos que
passam a ser P0 desta implementação:

1. latência de mutações ainda alta/timeout de cliente apesar de persistência;
2. roteamento de fontes incompatível com o universo/tipo de slot.

Evidências operacionais consideradas:

- projeto Naruto íntegro: 122 itens, domínio ANIME;
- estado compacto funcionando;
- relinkar_itens_lote retornando snapshot + próximo work packet;
- coleta avançando múltiplos termos em paralelo;
- continuar_processamento podendo estourar timeout no cliente;
- relinkar_itens_lote com observação de aproximadamente 69 s;
- Naruto chegando a PokeAPI / Spriters Resource / rotas Brave não configuradas;
- Naruto, Kakashi e Asuma chegando a SEM_FONTES_ATIVAS por roteamento inválido.

REGRA ESTRUTURAL:

PARALELISMO NÃO CORRIGE ROTEAMENTO.
PARALELISMO MULTIPLICA O COMPORTAMENTO DO ROTEADOR.

Portanto:

NARUTO + ANIME + ISOLATED
→ hard filter de domínio/universo/capability/configuração
→ fontes anime pesquisáveis compatíveis
→ somente depois score/fan-out.

Nunca:

NARUTO
→ PokeAPI / Bulbagarden / fonte de outro universo.

Também separar explicitamente:

DISCOVERY CAPABILITY
!=
MATERIALIZATION CAPABILITY.

Fandom/Wikia pode ser adaptador de materialização, mas o pipeline precisa de um
adapter pesquisável de discovery quando for necessário descobrir a URL.

SEM_FONTES_ATIVAS só é válido depois de todas as fontes compatíveis realmente
terem sido filtradas/tentadas. Se faltou adapter ou configuração, usar:

DISCOVERY_ADAPTER_MISSING
ou
ROUTING_CONFIGURATION_GAP.

FRASE DE ACEITE:

"NÃO FAZER O APP ERRAR MAIS RÁPIDO.
 PRIMEIRO ESCOLHER AS ROTAS CERTAS.
 DEPOIS ESCALAR O FAN-OUT."
