CORVO LIBRARY V61.6 — FAST ACK PARA DECISÕES DO SUPERVISOR

PROBLEMA CONFIRMADO NA V61.5

aplicar_decisoes_supervisor_lote ainda executava inline:

MCP
→ qaAutomaticProject
→ applyProjectQaDecisions
→ registerQaBatch
→ freezeApprovedItem
→ R2 GET/PUT
→ asset D1
→ usage
→ PITEM
→ fan-out
→ refresh summary
→ snapshot
→ resposta

Portanto uma chamada única não significava caminho rápido. Dez aprovações ainda podiam bloquear o request por dezenas de segundos/minutos.

V61.6 — NOVO CAMINHO

Supervisor
→ aplicar_decisoes_supervisor_lote
→ valida lease + payload
→ D1 batch atômico:
   operation_results + supervisor_decision_jobs
→ ACK QUEUED imediato
→ resposta MCP termina

DEPOIS DO ACK

Cloudflare waitUntil / cron
→ processSupervisorDecisionJobs
→ claim por lease
→ slice durável de decisões
→ qaAutomaticProject(processar_apos=false)
→ registerQaBatch
→ freeze/catalogação/R2/usage
→ PITEM/fan-out
→ grava progresso
→ COMPLETED

RECUPERAÇÃO

obter_resultado_operacao(operation_id)

Estados observáveis:
- RUNNING + result.phase=QUEUED
- RUNNING + result.phase=PROCESSING
- RUNNING + result.phase=RETRYING
- COMPLETED
- FAILED

O operation_id é o recibo durável e idempotente. Repetir a mesma operação não cria outro job.

PERSISTÊNCIA ATÔMICA

A criação do recibo e do job usa db.batch do D1. Assim o Supervisor não recebe ACK de uma decisão que não tenha trabalho persistido correspondente.

RETOMADA

supervisor_decision_jobs possui:
- status
- attempts
- lease_owner
- lease_expires_at
- progress_json
- cursor

Um Worker interrompido não perde a operação. Após expiração do lease, o job volta para QUEUED e o cron/Data Plane retoma.

PARALELISMO DA FINALIZAÇÃO

registerQaBatch deixou de congelar PITEMs distintos estritamente em série.
Até 8 grupos de itens diferentes podem finalizar em paralelo.
Decisões repetidas do mesmo item permanecem sequenciais para evitar corrida de estado.

O job trabalha em slices de até 12 decisões. Isso mantém checkpoints frequentes e reduz o risco de um waitUntil longo demais.

COMPATIBILIDADE

O nome aplicar_decisoes_supervisor_lote foi preservado.
Agentes existentes não precisam trocar de ferramenta.
O retorno ainda contém next_work_packet/next_actions vazios no ACK por compatibilidade; o pacote autoritativo é gravado no resultado final.

A ferramenta continua aceitando:
- APROVADO
- REJEITADO
- RELINK_REQUIRED
- CORRECAO_TECNICA_PERMITIDA

O teto lógico foi ampliado para 200 decisões por operação. A finalização divide internamente em slices seguros.

META

Tempo do request MCP passa a depender de:
- autenticação/lease;
- validação;
- poucas operações D1.

Ele não depende mais do tempo de:
- leitura/cópia R2;
- criação/reuso de asset;
- registro de uso;
- congelamento dos arquivos;
- fan-out;
- atualização final do projeto.

A meta arquitetural é ACK em centenas de milissegundos ou poucos segundos, enquanto o trabalho pesado continua internamente.
