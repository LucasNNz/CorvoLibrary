======================================================================
1. RESULTADO
======================================================================

A V55 acrescenta uma camada operacional multi-worker sobre a V54 sem remover o
mecanismo anterior de lease do Supervisor. A V54 continua servindo como
compatibilidade de supervisão por projeto; a escala de produção usa filas
independentes e a ferramenta MCP assumir_proximo_trabalho.

O núcleo implementado é:

FILA POR ETAPA + DOMÍNIO
-> FIFO
-> SKIP LOCKED equivalente
-> LEASE GRANULAR
-> HEARTBEAT POR ATIVIDADE REAL
-> WATCHDOG
-> IDEMPOTÊNCIA
-> LIMITES DE CONCORRÊNCIA
-> FAIRNESS POR PROJETO
-> TELEMETRIA OPERACIONAL
-> PAINEL OPERACIONAL / GERENCIAL

Não existe lock global da Biblioteca.

======================================================================
2. MODELO DE FILA / FIFO
======================================================================

A fila é derivada do estado canônico do projeto/item e persistida em
worker_work_items para aquisição e telemetria.

Ordenação aplicada na aquisição:

priority DESC
resume_priority DESC
original_ready_at ASC
attempts ASC
id ASC

O trabalho mais antigo ocupado não bloqueia os seguintes. Cada tentativa de
lease usa UPDATE condicional no D1. Se outro worker ganhou a corrida, changes=0
e o worker procura o próximo elegível.

A retomada preserva original_ready_at e ganha resume_priority, portanto queda de
worker não empurra o trabalho para o fim da fila.

======================================================================
3. LEASES GRANULARES
======================================================================

Tabela principal: worker_work_items.

O contrato é genérico por scope_type/scope_id e permite granularidade por
unidade operacional. Na síntese automática atual são usados:

- PROJECT para etapas exclusivas do projeto, como SCRIPT/ORGANIZAÇÃO;
- ITEM para coleta/materialização/QA/relink/correção técnica;
- EXPORT_JOB para ZIP/exportação independente.

O schema não fixa enum de scope_type, permitindo TARGET/BATCH/STAGE adicionais
sem migração estrutural pesada quando uma rota futura precisar de unidade
separada. Hoje ITEM é a granularidade fina aplicada aos targets do projeto.

TTL inicial: 10 minutos.
Watchdog lógico: 2 minutos.
Renovação: somente por atividade MCP real; não há ping artificial.

5. MULTI-NICHO
======================================================================

Domínio persistido em:

- automatic_projects.project_domain;
- automatic_project_items.item_domain;
- worker_work_items.project_domain;
- worker_sessions.worker_domain;
- source_profiles.domain;
- stage_metrics / eventos / snapshots / project_runs / export_jobs.

Domínios previstos:
ANIME, FOOTBALL, GAMES, GEEK, CARTOON, GENERAL e MULTI.

Regra padrão:
worker_domain == project_domain.

Worker MULTI pode operar mais de um domínio.
allowed_domains permite fallback explícito por worker.
fallback_between_domains permanece false por padrão.

Assim um worker ANIME não assume FOOTBALL por acidente.

Itens aprovados/congelados/resolvidos não retornam à fila.

======================================================================
8. WATCHDOG / QUEDA DE WORKER
======================================================================

runWorkerWatchdog varre leases granulares expirados.

Ao expirar:
- só a unidade daquele worker é liberada;
- status volta a READY quando requeue_expired_lease=true;
- resume_priority=1;
- original_ready_at é preservado;
- sessão antiga vira ABANDONADA;
- eventos LEASE_EXPIRED e WORK_ITEM_REQUEUED são registrados;
- nenhum asset, arquivo, QA ou resultado válido é apagado.

Uma execução antiga que reaparece não possui mais lease e recebe
WORK_ITEM_REASSIGNED ao tentar mutação.

O scheduled() do Worker executa tanto o watchdog legado V54 quanto o watchdog
granular V55. O ambiente de deploy ainda precisa associar o Cron/Scheduled
Trigger ao Worker para execução totalmente autônoma no intervalo desejado.

18. OBSERVAÇÃO DE DEPLOY
======================================================================

O código contém scheduled() para os watchdogs V54+V55, porém
.openai/hosting.json continua declarando apenas D1 e R2. Para watchdog periódico
independente de tráfego, o Worker publicado deve receber Scheduled/Cron Trigger
no ambiente de hospedagem.

Mesmo sem esse trigger, assumir_proximo_trabalho chama watchdog e sincronização
antes da aquisição, permitindo recuperação oportunista quando um novo worker
entra.

======================================================================
19. RESULTADO OPERACIONAL
======================================================================

Com a V55, a Biblioteca deixa de serializar toda a produção em um Supervisor
único. O modelo passa a ser:

SCRIPT por nicho -> workers independentes
COLETA por nicho -> workers independentes
MATERIALIZAÇÃO por nicho -> workers independentes
QA por nicho -> workers independentes
RELINK/CORREÇÃO -> workers independentes
ORGANIZAÇÃO -> etapa exclusiva quando necessário
EXPORTAÇÃO/ZIP -> EXPORT_JOB independente

Cada fila preserva FIFO, pula unidades ocupadas, usa lease próprio e mantém o
estado real na Biblioteca.
