ESPECIFICAÇÃO — BS14 FIFO + MULTI-WORKER + MULTI-NICHO + PAINEL OPERACIONAL
BIBLIOTECA SEMÂNTICA 14

OBJETIVO

Evoluir a Biblioteca Semântica 14 para operar como um núcleo de produção multiagente, multi-nicho e altamente observável, suportando:

- ordem de chegada (FIFO);
- comportamento equivalente a skip locked;
- múltiplos workers simultâneos;
- leases granulares;
- retomada automática;
- isolamento por nicho;
- filas por etapa;
- compatibilidade entre worker e domínio;
- painel operacional em tempo real;
- dashboard gerencial/diretoria;
- métricas por etapa, projeto, nicho e worker;
- robustez para escalar para vários tipos de produção.

Esta especificação complementa a implementação anterior de:
HEARTBEAT + LEASE + WATCHDOG + PRONTO_PARA_RETOMADA.


==================================================
1. VISÃO GERAL
==================================================

A Biblioteca Semântica 14 não deve funcionar apenas como repositório.

Ela deve atuar como uma plataforma operacional de produção.

Modelo desejado:

PROJETOS
→ entram por nicho
→ passam por filas por etapa
→ são processados por múltiplos workers
→ possuem monitoramento em tempo real
→ geram histórico operacional
→ alimentam painel de produção e painel gerencial

A arquitetura deve servir tanto para anime quanto para futuros nichos, como futebol, games, geek, cartoon e outros.


==================================================
2. PRINCÍPIO GERAL
==================================================

A Biblioteca não deve possuir um lock global único.

Ela deve funcionar como um sistema de filas com múltiplos workers especializados.

Cada worker assume apenas uma unidade de trabalho compatível com:

- sua função;
- seu nicho;
- o estado do projeto/item;
- os limites de concorrência;
- as dependências da etapa.


==================================================
3. EXEMPLO DE CAPACIDADE
==================================================

A Biblioteca deve permitir, por exemplo:

3 agentes de roteiro
3 agentes de coleta
3 agentes de análise
3 agentes de organização
3 agentes de ZIP/exportação

em um mesmo nicho

E, no futuro:

3 agentes de coleta Anime
3 agentes de coleta Futebol
3 agentes de análise Anime
3 agentes de análise Futebol
3 agentes de roteiro Geral
3 agentes de exportação Geral

Todos simultaneamente, sem conflitos desnecessários.


==================================================
4. NÃO USAR LOCK GLOBAL
==================================================

NÃO implementar:

biblioteca_locked = true

NÃO implementar lease global da Biblioteca.

NÃO permitir que um único worker impeça todos os demais de trabalhar.

A concorrência deve ser controlada por unidade de trabalho, por etapa, por projeto e por nicho.


==================================================
5. NÍVEIS DE LEASE
==================================================

A Biblioteca deve suportar lease granular nos seguintes escopos:

PROJECT
STAGE
ITEM
TARGET
BATCH
EXPORT_JOB

Prioridade operacional:

ITEM/TARGET
→ quando a etapa permitir paralelismo fino

STAGE
→ quando a etapa exigir exclusividade dentro do projeto

PROJECT
→ apenas quando realmente necessário

EXPORT_JOB
→ para jobs de geração de ZIP e exportação


==================================================
6. EXEMPLO DE LEASE GRANULAR
==================================================

Projeto Naruto:

ITEM 017 / COLETA
→ Worker COLLECTOR-01

ITEM 018 / COLETA
→ Worker COLLECTOR-02

ITEM 019 / COLETA
→ Worker COLLECTOR-03

ITEM 005 / QA
→ Worker ANALYST-01

ITEM 006 / QA
→ Worker ANALYST-02

EXPORT_JOB-01
→ Worker ZIP-01

Todos simultaneamente.

Se um worker cair, apenas seu lease expira.


==================================================
7. FIFO — ORDEM DE CHEGADA
==================================================

A Biblioteca deve priorizar trabalhos pela ordem de chegada.

Regra padrão:

FIRST IN
FIRST OUT

Fonte de verdade recomendada:

ready_at

ou, na ausência dele:

created_at

Ordenação sugerida:

ORDER BY
    priority DESC,
    ready_at ASC,
    created_at ASC


==================================================
8. SKIP LOCKED
==================================================

A fila não deve parar quando o item mais antigo estiver ocupado.

Exemplo:

Projeto A
entrou 10:00
lease válido
ocupado

Projeto B
entrou 10:10
livre

Projeto C
entrou 10:20
livre

Novo worker entra.

Resultado esperado:

A → ocupado, pular
B → assumir
C → permanecer aguardando

Conceito:
FIFO + SKIP LOCKED


==================================================
9. NÃO ESPERAR O MAIS ANTIGO LIBERAR
==================================================

Se o item mais antigo estiver com lease válido:

NÃO bloquear a fila.

NÃO encerrar sem verificar os seguintes.

Deve procurar o próximo elegível mais antigo.


==================================================
10. SELEÇÃO DE TRABALHO
==================================================

A lógica conceitual deve ser:

1. filtrar fila pela função correta;
2. filtrar pelo nicho correto;
3. remover concluídos;
4. remover cancelados;
5. remover itens com dependências não satisfeitas;
6. remover leases válidos de outros workers;
7. incluir leases ausentes;
8. incluir leases expirados;
9. ordenar por prioridade e ordem de chegada;
10. adquirir atomicamente o primeiro elegível.


==================================================
11. AQUISIÇÃO ATÔMICA
==================================================

A seleção e a aquisição do lease devem ocorrer atomicamente.

Evitar:

SELECT item livre
→ depois UPDATE lease

Preferir:

transação
ou
compare-and-set
ou
UPDATE condicional

Apenas o worker que realmente adquirir o lease poderá prosseguir.


==================================================
12. WORKER_ID
==================================================

Cada agente deve possuir identidade própria.

Campos recomendados:

worker_id
worker_type
worker_domain
execution_id
started_at
last_seen_at
status

Exemplo:

worker_id = "COLLECTOR-02"
worker_type = "COLLECTOR"
worker_domain = "ANIME"
execution_id = "EXEC-ABC123"


==================================================
13. TIPOS DE WORKER
==================================================

Tipos iniciais sugeridos:

SCRIPT
COLLECTOR
MATERIALIZER
ANALYST
QA
RELINK
TECHNICAL_FIX
ORGANIZER
EXPORTER
ZIP
SUPERVISOR

A arquitetura deve permitir novos tipos sem migração pesada.


==================================================
14. FILAS POR FUNÇÃO
==================================================

Cada worker deve buscar apenas trabalhos compatíveis com sua função.

Exemplos:

SCRIPT
→ fila SCRIPT

COLLECTOR
→ fila COLETA

MATERIALIZER
→ fila MATERIALIZACAO

ANALYST / QA
→ fila PARA_ANALISE

RELINK
→ fila RELINK_REQUIRED

ORGANIZER
→ fila ORGANIZACAO

EXPORTER / ZIP
→ fila EXPORTACAO


==================================================
15. MULTI-NICHO
==================================================

A Biblioteca deve suportar múltiplos nichos dentro da mesma plataforma.

Exemplos de nicho:

ANIME
FOOTBALL
GAMES
GEEK
CARTOON
GENERAL

O nicho deve ser persistido em:

- projeto;
- item;
- fila;
- worker;
- perfis de coleta;
- perfis de QA;
- telemetria;
- dashboards.

Não tratar nicho apenas como informação decorativa.


==================================================
16. COMPATIBILIDADE ENTRE WORKER E NICHO
==================================================

Um worker só pode assumir trabalhos compatíveis com seu nicho.

Exemplo:

worker_domain = ANIME

Pode assumir:
- projetos ANIME
- itens ANIME
- filas ANIME

Não deve assumir:
- FOOTBALL
- GAMES
- outros nichos incompatíveis

salvo se existir política explícita de fallback.

Regra principal:

worker_domain must match project_domain


==================================================
17. POR QUE REFORÇAR O NICHO
==================================================

Mesmo que o contexto normalmente venha correto do chat, é importante reforçar a compatibilidade de nicho porque no futuro existirão:

- múltiplos chats;
- múltiplos agendamentos;
- múltiplos workers;
- múltiplas filas;
- múltiplos perfis de coleta e QA.

Sem esse reforço, um worker de futebol poderia, por erro, assumir um projeto de anime.


==================================================
18. ESPECIALIZAÇÃO POR NICHO
==================================================

A arquitetura deve permitir especialização real.

Exemplos:

COLLECTOR_ANIME
COLLECTOR_FOOTBALL
ANALYST_ANIME
ANALYST_FOOTBALL
QA_ANIME
QA_FOOTBALL

Cada nicho poderá ter:

- fontes específicas;
- query templates próprios;
- limites próprios;
- perfis de QA próprios;
- regras de aprovação específicas;
- layouts/presets específicos;
- perfis de exportação próprios.


==================================================
19. WORKER_DOMAIN
==================================================

Adicionar campo obrigatório no contrato do worker:

worker_domain

Valores sugeridos:

ANIME
FOOTBALL
GAMES
GEEK
CARTOON
GENERAL

Pode haver também:

MULTI

para workers explicitamente autorizados a operar mais de um nicho.


==================================================
20. PROJECT_DOMAIN
==================================================

Adicionar no projeto:

project_domain

Adicionar no item:

item_domain

Se item_domain não for informado, herdar de project_domain.

Isso permite filtragem robusta de filas e métricas por nicho.


==================================================
21. FALLBACK ENTRE NICHOS
==================================================

Por padrão:

fallback entre nichos = desativado

Ou seja:

worker ANIME não pega FOOTBALL.

Se futuramente desejar permitir fallback controlado, usar política explícita, por exemplo:

allowed_domains = ["ANIME", "GEEK"]

ou

worker_domain = MULTI


==================================================
22. FILA NÃO PRECISA SER TABELA SEPARADA
==================================================

A fila pode ser derivada do estado persistido.

Exemplo:

status_pipeline
stage
project_domain
ready_at
lease_owner
lease_expires_at

Uma tabela de queue pode existir por performance, mas a fonte de verdade deve continuar sendo o estado canônico.


==================================================
23. LIMITES DE CONCORRÊNCIA
==================================================

Adicionar limites configuráveis por worker_type.

Exemplos:

max_workers_script = 3
max_workers_coleta = 3
max_workers_materializacao = 5
max_workers_analise = 3
max_workers_qa = 3
max_workers_organizacao = 3
max_workers_exportacao = 3

Além disso, prever limites por nicho:

max_workers_coleta_anime = 3
max_workers_coleta_football = 3
max_workers_analise_anime = 3
max_workers_analise_football = 3


==================================================
24. NÃO FIXAR O SISTEMA EM 3
==================================================

O número 3 é apenas configuração inicial.

A Biblioteca deve poder escalar para:

5
10
20

ou mais workers por função e nicho, dentro dos limites técnicos de:

D1
R2
Cloudflare
MCP
CPU
rede
fontes externas
rate limits


==================================================
25. LIMITE POR PROJETO
==================================================

Além do limite por função e por nicho, permitir limite por projeto.

Exemplos:

max_collectors_per_project = 3
max_analysts_per_project = 3

Isso evita que um projeto grande monopolize toda a capacidade.


==================================================
26. FAIRNESS ENTRE PROJETOS
==================================================

FIFO puro por item pode fazer um projeto enorme dominar a fila.

Opcionalmente implementar fairness.

Exemplo:

Projeto A tem 100 itens antigos.
Projeto B acabou de entrar com 10 itens.

A Biblioteca pode manter FIFO, mas limitar a quantidade de workers por projeto, liberando outros workers para B, C e D.

Isso aumenta throughput global.


==================================================
27. ORDEM DE PRIORIDADE
==================================================

Regra recomendada:

1. prioridade manual explícita;
2. retomadas críticas;
3. ordem de chegada;
4. menor número de tentativas;
5. desempate por ID.

Exemplo:

ORDER BY
    priority DESC,
    resume_priority DESC,
    ready_at ASC,
    attempts ASC,
    id ASC


==================================================
28. PRONTO_PARA_RETOMADA
==================================================

Itens/projetos cujo lease expirou devem voltar à fila.

Não devem ir automaticamente para o final.

Preservar:

original_ready_at

para manter a antiguidade lógica do trabalho.


==================================================
29. NÃO PENALIZAR QUEDA DE CHAT
==================================================

Se um worker cair:

NÃO redefinir created_at.

NÃO jogar o trabalho para o fim da fila.

NÃO apagar prioridade.

O trabalho deve manter sua posição lógica.


==================================================
30. HEARTBEAT POR ATIVIDADE REAL
==================================================

Manter a regra:

operações reais renovam lease.

Não criar ping artificial do MCP apenas para heartbeat.

Campos:

lease_last_seen_at
lease_expires_at

TTL inicial recomendado:

10 minutos

Watchdog:

a cada 2 minutos


==================================================
31. SE UM WORKER MORRER
==================================================

Exemplo:

COLLECTOR-02 trabalhando no ITEM-018.

Chat cai.

COLLECTOR-01 e COLLECTOR-03 continuam normalmente.

Após expiração do lease:

ITEM-018
→ PRONTO_PARA_RETOMADA

Outro collector do mesmo nicho pode assumir.

A falha de um worker não deve impactar os demais.


==================================================
32. EXECUÇÃO ANTIGA RETORNANDO
==================================================

Se o worker antigo reaparecer depois que o lease foi assumido por outro:

bloquear alterações.

Condição:

execution_id enviado != execution_id dono atual

Retornos sugeridos:

LEASE_NOT_OWNED
SUPERVISOR_REPLACED
WORK_ITEM_REASSIGNED


==================================================
33. IDEMPOTÊNCIA
==================================================

Toda operação deve ser idempotente.

Especialmente:

SCRIPT
REQUIREMENTS
target creation
coleta
materialização
QA
aprovação
freeze
relink
correção técnica
organização
ZIP
exportação

Chaves sugeridas:

project_id
project_domain
stage
item_id
candidate_id
operation_type
idempotency_key


==================================================
34. MATERIALIZAÇÃO PARALELA
==================================================

Vários workers podem materializar simultaneamente desde que:

- estejam em itens diferentes;
- respeitem rate limits;
- respeitem limites de concorrência;
- não escrevam o mesmo materialization_id;
- usem idempotency_key;
- respeitem o nicho do item/projeto.


==================================================
35. QA PARALELO
==================================================

Vários agentes de análise podem trabalhar simultaneamente.

Exemplo:

ANALYST-01 ANIME
→ ITEM 10

ANALYST-02 ANIME
→ ITEM 11

ANALYST-03 FOOTBALL
→ ITEM 12

Nenhum deve gravar decisão no mesmo item simultaneamente.


==================================================
36. ROTEIRO PARALELO
==================================================

Vários agentes de roteiro podem atuar em projetos diferentes simultaneamente.

Se a etapa roteiro for exclusiva dentro do mesmo projeto, usar lease de STAGE.

Exemplo:

PROJECT-A / SCRIPT / ANIME
→ SCRIPT-WORKER-01

PROJECT-B / SCRIPT / FOOTBALL
→ SCRIPT-WORKER-02


==================================================
37. ORGANIZAÇÃO PARALELA
==================================================

Workers de organização podem atuar em:

- renomeação segura;
- organização por slot;
- montagem de manifesto;
- reconciliação de arquivos;
- preparação de exportação.

Evitar alterações concorrentes sobre o mesmo manifesto/arquivo.


==================================================
38. ZIP / EXPORTAÇÃO PARALELA
==================================================

Cada export_job deve possuir lease próprio.

Exemplo:

EXPORT-A
→ ZIP-WORKER-01

EXPORT-B
→ ZIP-WORKER-02

Se o mesmo conjunto de assets já possuir ZIP reutilizável:

usar cache/idempotência em vez de gerar novamente.


==================================================
39. DEPENDÊNCIAS ENTRE ETAPAS
==================================================

A Biblioteca deve liberar trabalho apenas quando pré-requisitos estiverem satisfeitos.

Exemplos:

QA
→ só entra na fila se houver materialização real

ZIP
→ só entra se os assets obrigatórios estiverem aprovados

RELINK
→ entra após rejeição ou gap

ORGANIZAÇÃO
→ só entra quando os assets necessários existirem


==================================================
40. STAGE_READY_AT
==================================================

Adicionar opcionalmente:

stage_ready_at

Esse timestamp representa quando a unidade ficou disponível para aquela fila.

Exemplo:

item criado 10:00
materialização terminou 10:30
QA ficou elegível 10:30

Para fila QA:

stage_ready_at = 10:30


==================================================
41. FIFO POR FILA / ETAPA
==================================================

Cada fila deve ser FIFO de forma independente.

Exemplo:

fila COLETA
→ mais antigo elegível primeiro

fila QA
→ mais antigo aguardando QA primeiro

fila ZIP
→ exportação mais antiga pronta primeiro

Não usar fila global única para tudo.


==================================================
42. FUNÇÃO MCP RECOMENDADA
==================================================

Criar ferramenta genérica:

assumir_proximo_trabalho

Entrada:

worker_type
worker_id
worker_domain
execution_id
project_id opcional

Saída:

work_item_id
project_id
project_domain
stage
lease_expires_at
payload
next_action

Ela deve:

1. validar limite de workers;
2. validar compatibilidade de nicho;
3. localizar trabalho elegível;
4. aplicar FIFO;
5. pular leases válidos;
6. adquirir lease atomicamente;
7. retornar apenas o trabalho efetivamente adquirido.


==================================================
43. FUNÇÃO DE LIBERAÇÃO
==================================================

Criar:

concluir_trabalho_worker

Entrada:

worker_id
worker_domain
execution_id
work_item_id
resultado

Ela deve:

- validar dono do lease;
- persistir resultado;
- marcar unidade concluída;
- liberar lease;
- atualizar próxima etapa;
- definir stage_ready_at da próxima fila.


==================================================
44. FUNÇÃO DE FALHA
==================================================

Criar:

registrar_falha_worker

Ela deve diferenciar:

ERRO_REAL
RETRYABLE
RELINK_REQUIRED
WAITING_DEPENDENCY
ABANDONED_BY_LEASE


==================================================
45. WATCHDOG
==================================================

O watchdog deve varrer leases expirados em qualquer fila e nicho.

Exemplo:

COLLECTOR
ANALYST
ZIP
SCRIPT
ORGANIZER

Ao expirar:

- marcar execução abandonada;
- preservar estado;
- liberar item;
- retornar unidade à fila;
- manter ordem original quando apropriado.


==================================================
46. NÃO REPROCESSAR CONCLUÍDOS
==================================================

Uma unidade concluída nunca deve voltar à fila apenas porque lease expirou depois.

O watchdog deve verificar:

status != CONCLUIDO

59. NÃO MISTURAR ESTADO COM ANALYTICS
==================================================

O estado operacional principal deve continuar leve e rápido.

Telemetria, histórico e analytics devem ir para estruturas próprias.

Sugestão de tabelas/coleções lógicas:

projects
project_items
worker_sessions
worker_events
stage_metrics
queue_snapshots
project_runs
export_jobs

Isso evita que a tabela principal da operação fique pesada.

60. ÚLTIMA AÇÃO OPERACIONAL

Adicionar campo útil para o painel:

last_action

Exemplo:

Isso melhora muito a observabilidade.


==================================================
61. CAPACITY PLANNING
==================================================

A Biblioteca deve futuramente apoiar planejamento de capacidade.

Exemplos de insights:

- Coleta Anime está a 92% de utilização
- QA Futebol tem backlog estimado de 4h
- ZIP está ocioso
- Serão necessários +2 analysts se entrarem mais 3 projetos hoje
- Coleta Anime é o gargalo recorrente da semana

Isso transforma a Biblioteca em ferramenta de decisão.


==================================================
62. RATE LIMITS E FONTES POR NICHO
==================================================

Workers de coleta/materialização devem respeitar:

- limites por host;
- limites por fonte;
- limites por nicho;
- circuit breaker;
- timeout;
- concorrência máxima;
- cooldown.

Paralelismo não pode significar bombardear as fontes.


==================================================
63. PERFIS POR NICHO
==================================================

Cada nicho deve poder ter seus próprios:

- source_profiles;
- query templates;
- negative terms;
- perfis de QA;
- perfis de correção técnica;
- presets operacionais;
- padrões de exportação.

Isso aumenta a robustez da Biblioteca para vários nichos.


==================================================
64. AGENDAMENTOS ESPECIALIZADOS
==================================================

Pode haver vários agendamentos especializados.

Exemplo:

Agente Roteiro Anime
→ busca fila SCRIPT + ANIME

Agente Coleta Anime
→ busca fila COLETA + ANIME

Agente Análise Anime
→ busca fila QA + ANIME

Agente Coleta Futebol
→ busca fila COLETA + FOOTBALL

Agente ZIP Geral
→ busca fila EXPORTACAO + MULTI

Cada um consulta a Biblioteca e assume apenas trabalhos compatíveis.


==================================================
65. VÁRIAS EXECUÇÕES DO MESMO TIPO
==================================================

Também pode haver múltiplas execuções do mesmo tipo e nicho.

Exemplo:

COLLECTOR-ANIME-A
COLLECTOR-ANIME-B
COLLECTOR-ANIME-C

Todos chamam assumir_proximo_trabalho.

Aquisição atômica garante que cada um receba unidade diferente.


==================================================
66. FIFO POR FILA, NÃO FILA GLOBAL ÚNICA
==================================================

Recomendação:

FIFO por fila/etapa.

Não usar uma única fila global para tudo.

Um ZIP antigo não deve impedir uma coleta nova se existem workers diferentes.

==================================================
71. REGRAS DE ACEITE
==================================================

[ ] A fila respeita ordem de chegada.

[ ] Itens ocupados não bloqueiam os seguintes.

[ ] O sistema implementa comportamento equivalente a SKIP LOCKED.

[ ] Dois workers não conseguem assumir a mesma unidade.

[ ] Leases são granulares.

[ ] Não existe lock global desnecessário.

[ ] Vários workers do mesmo tipo podem trabalhar simultaneamente.

[ ] Workers de tipos diferentes podem trabalhar simultaneamente.

[ ] Workers de nichos diferentes podem trabalhar simultaneamente.

[ ] Cada worker só assume trabalho compatível com seu nicho.

[ ] Fallback entre nichos não ocorre sem política explícita.

[ ] Limites por função são configuráveis.

[ ] Limites por projeto são configuráveis.

[ ] Limites por nicho são configuráveis.

[ ] Queda de um worker não interrompe os demais.

[ ] Lease expirado devolve o trabalho à fila.

[ ] Trabalho retomado preserva sua antiguidade/prioridade.

[ ] Execução antiga não consegue escrever após perder lease.

[ ] Operações são idempotentes.

[ ] Projetos concluídos não voltam à fila.

[ ] Dependências de etapa são respeitadas.

[ ] FIFO é aplicado por fila.

[ ] Fairness evita monopolização por um projeto.

[ ] ZIP/exportação possui jobs independentes.

[ ] Coleta e materialização respeitam rate limits.

[ ] O painel operacional mostra workers, filas e saturação.

[ ] O painel gerencial mostra métricas por etapa, projeto e nicho.

[ ] Existem gráficos de tempo médio e capacidade.

[ ] A telemetria é suficiente para capacity planning.

73. RESULTADO ESPERADO
==================================================

A Biblioteca Semântica 14 deve funcionar como uma plataforma de produção multiagente, multi-nicho e observável.

Modelo:

ROTEIROS
→ fila SCRIPT por nicho
→ vários workers

COLETA
→ fila COLETA por nicho
→ vários workers

MATERIALIZAÇÃO
→ fila MATERIALIZACAO por nicho
→ vários workers

ANÁLISE
→ fila QA por nicho
→ vários workers

ORGANIZAÇÃO
→ fila ORGANIZACAO por nicho
→ vários workers

ZIP
→ fila EXPORTACAO por nicho ou MULTI
→ vários workers

Cada fila:

FIFO
+
SKIP LOCKED
+
LEASE GRANULAR
+
HEARTBEAT
+
WATCHDOG
+
IDEMPOTÊNCIA
+
COMPATIBILIDADE POR NICHO

Se um worker cair:

somente seu trabalho é liberado após expiração do lease.

Se um trabalho antigo estiver ocupado:

o próximo elegível é processado.

Se houver vários agentes:

todos podem trabalhar simultaneamente sem duplicar a mesma unidade.

A operação deve ser totalmente visível no painel de produção e mensurável no painel gerencial.
