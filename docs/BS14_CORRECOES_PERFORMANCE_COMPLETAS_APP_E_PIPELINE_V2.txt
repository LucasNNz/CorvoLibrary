2. PROBLEMA MAIS URGENTE: UM ITEM NÃO PODE PARAR O PROJETO
============================================================

SITUAÇÃO ATUAL OBSERVADA
O processamento determinístico para quando chega a:
- QA visual;
- relink;
- decisão semântica;
- decisão de fonte.

Isso faz sentido para aquele ITEM.
Não faz sentido parar o PROJETO inteiro.

EXEMPLO ERRADO:
item 001 precisa de QA
→ pipeline para
→ itens 002–122 deixam de avançar
→ Supervisor analisa 001
→ pipeline volta
→ próximo bloqueio
→ repete.

Em um projeto de 122 imagens, esse desenho é lento demais.

COMPORTAMENTO OBRIGATÓRIO NOVO:
item 001 precisa de QA
→ marcar 001 = WAITING_SUPERVISOR
→ liberar worker
→ continuar 002, 003, 004...
→ acumular pacote de QA
→ Supervisor decide vários de uma vez.

A fila deve operar com SKIP LOCKED / SKIP WAITING.

ESTADOS QUE NÃO PODEM BLOQUEAR OUTROS ITENS:
- WAITING_VISUAL_QA
- RELINK_REQUIRED
- SOURCE_DECISION_REQUIRED
- TECHNICAL_CORRECTION_REQUIRED
- WAITING_FAMILY_SEED

Somente o item fica parado.
O projeto continua.

============================================================
3. CRIAR FILAS INDEPENDENTES POR ETAPA
============================================================

Não usar uma única fila linear.

Criar ao menos:

FILA A — LINKAGEM / PREPARAÇÃO SEMÂNTICA
FILA B — DESCOBERTA / COLETA
FILA C — MATERIALIZAÇÃO
FILA D — PRECHECK TÉCNICO
FILA E — QA VISUAL
FILA F — RELINK
FILA G — CORREÇÃO TÉCNICA PERMITIDA
FILA H — FREEZE / LOG / BIBLIOTECA
FILA I — ZIP

Cada etapa deve consumir somente itens elegíveis.

Um item em QA não deve ocupar worker de coleta.
Um relink não deve impedir materialização de outros itens.
ZIP só espera o gate final, não precisa interferir nas etapas anteriores.

4. AUMENTAR O PARALELISMO DO PROJETO
============================================================

Estado atual:
- globalConcurrency = 8
- projeto Naruto = parallelism 3

Para projetos grandes, 3 é pouco.

Sugestão inicial segura:
- LINKAGEM/PREPARAÇÃO: 10 itens

============================================================
8. CIRCUIT BREAKER PRECISA SER MAIS INTELIGENTE
============================================================

Foi observado:
static.wikia.nocookie.net
- 102 sucessos
- 5 falhas
- mesmo assim apareceu OPEN por falhas recentes.

Isso pode punir uma fonte excelente por duas falhas locais.

Não usar apenas:
“2 falhas consecutivas = host inteiro bloqueado”

Usar combinação:
- taxa de sucesso histórica;
- taxa de falha em janela recente;
- tipo de erro;
- latência;
- 403/429;
- timeout;
- falha de URL específica;
- sucesso de outras URLs do mesmo host.

Exemplo:
host com 102 sucessos e 5 falhas
→ não abrir breaker global agressivo.

Preferir:
URL falhou
→ descartar URL
→ tentar outra URL do mesmo host.

Abrir breaker global somente se:
- falha generalizada do host;
- vários itens diferentes falham;
- taxa de erro da janela passa limite.

============================================================
9. DIFERENCIAR FALHA DE URL, FALHA DE FONTE E FALHA SEMÂNTICA
============================================================

Hoje essas categorias podem produzir decisões desnecessárias.

Criar classificação clara:

URL_404
→ descartar URL automaticamente.

URL_403
→ tentar alternativa/resolver URL;
→ após limite, marcar rota como ruim.

SOURCE_EMPTY
→ trocar fonte/query automaticamente.

SOURCE_NOT_CONFIGURED
ex.: Brave sem API key
→ desativar aquela fonte automaticamente;
→ não pedir Supervisor toda vez.

SEMANTIC_REJECTION
→ imagem materializou, mas não representa o conceito;
→ descartar candidata;
→ próxima candidata/fonte/query;
→ relink somente quando necessário.

TECHNICAL_FAILURE
→ arquivo corrompido, formato inválido, tamanho ruim etc.
→ outra candidata.

Nenhuma dessas falhas individuais deve bloquear o projeto inteiro.

23. RESUMO EXECUTIVO
============================================================

O problema atual não é falta de velocidade de download.

O problema é que a arquitetura ainda se comporta de forma excessivamente serial:
UM ITEM → DECISÃO → UM ITEM → DECISÃO.

Para 120 imagens precisamos:
MUITOS ITENS EM PARALELO
→ MUITAS CANDIDATAS
→ MATERIALIZAÇÃO PARALELA
→ QA EM LOTE
→ RELINK EM LOTE
→ FREEZE INDEPENDENTE
→ SOMENTE GAPS CONTINUAM.

A mudança mais importante é esta:

“UMA PENDÊNCIA BLOQUEIA SOMENTE O ITEM, NUNCA O PROJETO.”

Isso deve ser a regra estrutural da Biblioteca Semântica 14.
============================================================
24. NOVO DIAGNÓSTICO: LATÊNCIA DO APP / MCP TAMBÉM É GARGALO
============================================================

A lentidão não está apenas na coleta.

Existe um segundo custo importante:
LATÊNCIA DE CONTROLE.

Operações aparentemente simples também consomem tempo:
- consultar projeto;
- listar projetos;
- listar decisões;
- listar candidatas;
- obter status;
- abrir painel;
- reconciliar;
- registrar QA;
- atualizar estado;
- buscar assets;
- consultar lote.

Em um pipeline com 120 imagens, centenas dessas pequenas operações podem ocorrer.

Mesmo que uma chamada demore apenas alguns segundos:
300 chamadas × 2 s = 10 minutos
300 chamadas × 5 s = 25 minutos
300 chamadas × 10 s = 50 minutos

Portanto:
OTIMIZAR DOWNLOAD SEM OTIMIZAR A CAMADA DE CONTROLE NÃO RESOLVE.

============================================================
25. REGRA DE PERFORMANCE PARA UM APP OPERACIONAL
============================================================

Consultas simples e leituras de estado devem parecer praticamente instantâneas.

Meta inicial recomendada no backend, sem contar inferência do ChatGPT:

- health/status simples: P50 < 100 ms / P95 < 300 ms
- consulta por ID indexado: P50 < 100 ms / P95 < 300 ms
- listagem pequena paginada: P50 < 150 ms / P95 < 500 ms
- busca filtrada/indexada: P95 < 700 ms
- mutação simples: P95 < 500 ms
- operação pesada: assíncrona ou separada, nunca escondida dentro de uma consulta simples

Essas metas são referências de engenharia, não garantias absolutas.

O principal princípio é:
READ simples NÃO pode disparar trabalho pesado.

→ somente o item.

→ quando necessário.

============================================================
31. PAGINAÇÃO POR CURSOR, NÃO OFFSET
============================================================

Listagens grandes devem usar cursor estável:

cursor = updated_at + id

Evitar:
OFFSET 500
OFFSET 1000
OFFSET 5000

Preferir:
WHERE (updated_at,id) > (?,?)
ORDER BY updated_at,id
LIMIT 50

Aplicar em:
- assets;
- projetos;
- candidatos;
- eventos;
- decisões;
- logs;
- materializações.

============================================================
32. ÍNDICES D1 OBRIGATÓRIOS
============================================================

Auditar EXPLAIN QUERY PLAN de todas as consultas críticas.

Criar índices compostos alinhados às filas e consultas.

Exemplos conceituais:

project_items(project_id, status, priority, created_at)
project_items(project_id, target_file)

A implementação deve usar nomes reais das tabelas.

CRITÉRIO:
nenhuma consulta quente pode depender de full table scan evitável.

============================================================
33. ELIMINAR N+1 QUERIES
============================================================

Investigar padrões:

SELECT itens
→ para cada item SELECT candidatas
→ para cada candidata SELECT arquivo
→ para cada item SELECT decisão

Com 120 itens isso explode o número de consultas.

Substituir por:
- joins controlados;
- SELECT ... WHERE item_id IN (...);
- agregações;
- batch reads;
- materialized summary.

Medir:
db_query_count por chamada MCP.

Meta:
uma listagem simples não deve executar centenas de queries.

============================================================
34. NÃO CONSULTAR R2 PARA LISTAR ESTADO
============================================================

R2 deve armazenar arquivo/binário.

D1 deve possuir metadados necessários:
- r2_key
- mime
- width
- height
- bytes
- hash
- status
- timestamps.

Listar projeto ou asset NÃO deve:

R2 só deve ser acessado quando:

- materializar;
- gerar ZIP;
- operação explicitamente relacionada ao objeto.

============================================================
35. CACHE DE LEITURAS QUENTES
============================================================

- perfis de coleta;
- configuração;
- fontes;
- blacklist;
- capacidade;
- universe routing;
- presets.

TTL possível:

Por request:

Por Worker:

============================================================
36. UM REQUEST = UMA TRANSAÇÃO LÓGICA
============================================================

Evitar que uma ação do Supervisor exija cadeia:

call A
→ pegar ID
→ call B
→ pegar estado
→ call C
→ reconciliar
→ call D
→ confirmar.

Criar operações compostas idempotentes.

Exemplo:

resolver_qa_lote({
 decisions: [...]
})

deve:
- aplicar decisões;
- atualizar itens;
- congelar aprovados;
- enfileirar rejeitados;
- atualizar contadores;
- incrementar version;
- retornar snapshot final.

Não exigir uma consulta de confirmação se a própria mutação pode retornar o estado reconciliado.

============================================================
37. WRITE + RETURN STATE
============================================================

Toda mutação importante deve retornar:

{
 success,
 changed_items,
 project_version,
 project_counts,
 next_actions
}

Assim elimina:
WRITE
→ GET para confirmar
→ GET para descobrir próximo passo.

A resposta do WRITE já deve confirmar persistência.

============================================================
38. IDEMPOTÊNCIA PARA EVITAR RECONSULTA APÓS TIMEOUT
============================================================

Algumas chamadas já foram observadas como:
cliente recebe timeout
mas operação persiste no servidor.

Isso gera:
timeout
→ dúvida
→ consultar estado
→ talvez repetir
→ mais latência.

Toda mutação deve aceitar:
idempotency_key / operation_id

E permitir:
obter_resultado_operacao(operation_id)

Se timeout:
não repetir trabalho.
Consultar somente o resultado da operação.

Melhor:
o MCP/runtime deve conseguir recuperar a resposta persistida da mesma operação.

============================================================
39. TIMEOUT NÃO DEVE APAGAR RESULTADO
============================================================

Operações pesadas devem:

1. validar;
2. criar job;
3. persistir job_id;
4. retornar rápido.

O processamento continua no backend permitido pelo ambiente.

Status consultável por job_id.

IMPORTANTE:
isso se refere ao funcionamento do APP/Worker, não ao ChatGPT fazer trabalho em background.

A interface MCP não deve manter uma conexão longa esperando uma coleta inteira terminar.

55. CRITÉRIO DE ACEITE DA CAMADA DE APP
============================================================

Não basta “funcionar”.

Aceite somente se:

- listar projeto é rápido;
- abrir painel é rápido;
- consultar estado não reconcilia tudo;
- mutation retorna estado atualizado;
- não há GET de confirmação obrigatório;
- payload padrão é compacto;
- número de queries é conhecido;
- duração de cada fase é conhecida;
- 120 itens não multiplicam linearmente a latência de leitura;
- batch de 20 custa muito menos que 20 chamadas individuais;
- app continua responsivo enquanto pipeline executa.

Teste obrigatório:

A) 1 item
listar/consultar.

B) 120 itens
mesma consulta.

A consulta resumida de B NÃO pode ficar 120x mais lenta que A.

56. REGRA DE OURO DE PERFORMANCE
============================================================

O Supervisor deve gastar tempo DECIDINDO,
não ESPERANDO O APP.

E o app deve gastar tempo PRODUZINDO ASSETS,
não RECONSTRUINDO ESTADO.

Para 120 imagens:

ERRADO:
consultar → esperar
listar → esperar
abrir → esperar
decidir 1
gravar → esperar
consultar confirmação → esperar
repetir 120 vezes.

CORRETO:

→ processar 10–20 itens
→ resposta em lote
→ backend continua em paralelo
→ delta
→ novo lote.

============================================================
57. CONCLUSÃO ATUALIZADA
============================================================

Existem DOIS gargalos independentes e cumulativos:

GARGALO 1 — PIPELINE
trabalho excessivamente serial e bloqueado por decisões individuais.

GARGALO 2 — APP/MCP
muitas chamadas pequenas, consultas potencialmente pesadas, payloads grandes e falta de instrumentação por camada.

Resolver somente um deles não basta.

O alvo da próxima versão deve ser:

FAST CONTROL PLANE + PARALLEL DATA PLANE

CONTROL PLANE:
consultas, estado, decisões, filas e comandos rápidos.

DATA PLANE:
busca, download, materialização, QA/precheck e armazenamento paralelos.

O app precisa ser redesenhado para que o custo operacional não cresça proporcionalmente ao número de interações.
