2. REGRA DE OURO V61

TRABALHO READY + CAPACIDADE DISPONÍVEL = TRABALHO DEVE COMEÇAR AUTOMATICAMENTE.

O Supervisor não deve chamar ferramenta para cada item nem mandar CONTINUE entre estações determinísticas.

3. DISPATCHER INTERNO

Novo módulo:
lib/internal-worker-dispatcher.ts

Responsabilidades:
- sincronizar fila canônica;
- executar watchdog granular;
- escolher somente trabalho READY executável;
- respeitar FIFO + skip locked;
- respeitar worker_type, project_domain, capacidade e max_parallelism do plano;
- claim atômico em D1;
- criar worker_session interna;
- vincular PLAN_BRANCH ao lease;
- executar ciclo canônico do projeto;
- finalizar/yield da unidade;
- reencadear fila;
- publicar telemetria.

Transição:
READY → LEASED → RUNNING → COMPLETED/READY/WAITING_SUPERVISOR

4. ESCOPO SEGURO DO DATA PLANE INTERNO

O dispatcher automático consome somente scope_type=ITEM e etapas determinísticas:
- COLETA;
- MATERIALIZACAO;
- RELINK já autorizado.

Ele NÃO auto-consome QA visual.
Ele NÃO auto-completa EXPORT_JOB/ZIP sem executor específico.
Ele NÃO transforma ambiguidade visual/semântica em decisão automática.

QA e correções que exigem decisão permanecem WAITING_SUPERVISOR.

5. CLAIM ATÔMICO

A aquisição usa compare-and-set D1 equivalente a:

UPDATE worker_work_items
SET status='LEASED', lease_owner_worker_id=?, lease_execution_id=?, ...
WHERE id=?
  AND status='READY'
  AND (lease_expires_at IS NULL OR lease_expires_at<?)

Somente um consumidor vence. Não existe lock global.

6. WAKE-UP APÓS ACK

worker/index.ts foi conectado ao Data Plane.

Para MCP:
- tools/list, initialize, ping e leituras NÃO acordam produção;
- somente tools/call mutantes retornam header interno x-corvo-dispatch-wake=1;
- depois que handler.fetch produz a resposta, o Worker agenda o pump com ctx.waitUntil.

Assim:
Supervisor → supervisor_exchange → ACK
                              ↘ waitUntil → Data Plane

O cliente não espera busca/materialização.

7. DATA PLANE PUMP

Após uma mutação operacional, pumpDataPlane executa até 4 passes, respeitando um budget de parede de 25 s entre passes. Cada passe chama runSupervisorPlansTick, que por sua vez roda o dispatcher antes do fan-in.

Se ainda existir READY após o limite, o estado fica persistido e poderá continuar no próximo wake/cron. O objetivo é drenar o máximo possível no mesmo wake sem reintroduzir chamadas longas no Control Plane.

8. SELF-HEALING

O scheduled handler:
1. executa watchdog de Supervisor;
2. executa watchdog de workers;
3. executa o mesmo pump de Data Plane;
4. faz fan-in/status dos planos.

O código do scheduled hook está implementado. A execução periódica em produção depende de o ambiente de deploy possuir um Cron Trigger/Scheduler apontando para este Worker.

9. FAN-OUT CHUNKED

Nova configuração:
supervisor_plan_branch_insert_chunk_size = 20

Exemplo:
115 branches
→ 20
→ 20
→ 20
→ 20
→ 20
→ 15

Continua sendo UMA operação lógica do Supervisor.

createBranchesForPlan persiste cada chunk separadamente.

Se um chunk falhar:
- lança PLAN_BRANCH_INSERT_FAILED;
- branches parciais ativas são CANCELLED;
- plano vira FAILED;
- active_plan_id é removido;
- operation_id registra falha.

Planos vazios não devem permanecer ACCEPTED/DISPATCHING.

10. WIP DEFAULT

A V60 havia semeado supervisor_plan_max_wip=80.
A V61 migra somente esse default legado para 200.

Regra de migração:
- se valor atual = 80 → 200;
- se operador já customizou outro valor → preservar.

Isso permite fan-out de projetos como Naruto (~115 elegíveis) sem o Supervisor precisar conhecer limite interno do D1.

11. CONTINUAR_PROCESSAMENTO

Deixa de executar ciclo pesado síncrono.

Agora:
continuar_processamento
→ controlProject(continuar)
→ executeUntilDivergence
→ SUPERVISOR_PLAN
→ ACK
→ background dispatcher.

Input novo preferencial:
max_itens

max_etapas permanece apenas por compatibilidade de schema legado.

12. RELINK

RELINK automático só entra no dispatcher quando a rota foi explicitamente autorizada pelo plano/branch ou contém queries/preferred_sources definidas.

RELINK em WAITING_SUPERVISOR não é consumido automaticamente.

13. FAN-IN

refreshPlanBranches passou a observar:
- status canônico do item;
- stage canônico;
- lease ativo;
- lease perdido/expirado;
- QA/technical boundary.

RUNNING sem lease válido retorna para READY.
Item resolvido conclui branch.
QA/technical fica WAITING_SUPERVISOR.
