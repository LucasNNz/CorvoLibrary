ESPECIFICAÇÃO PARA IMPLEMENTAÇÃO — V1
DATA: 2026-08-27

1. OBJETIVO

Criar dentro da Biblioteca Semântica uma camada persistente de aprendizado operacional capaz de transformar gaps recorrentes em regras reutilizáveis.

REGRA CENTRAL:
“UM GAP RESOLVIDO UMA VEZ NÃO DEVE PRECISAR SER REDESCOBERTO EM OUTRO PROJETO EQUIVALENTE.”

Hoje o Supervisor pode encontrar problemas como:
- fonte incompatível com o universo;
- API sem credencial;
- 403/404 recorrentes;
- perfil inadequado;
- timeout excessivo;
- QA que rejeita sempre certa rota;
- relink recorrente;
- preset com exigência técnica;
- congestionamento de fila;
- conflitos de ZIP;
- comportamento específico de um domínio.

A solução não deve morrer naquela execução. Ela deve virar CONHECIMENTO OPERACIONAL EXECUTÁVEL.

Fluxo:
GAP → CLASSIFICAÇÃO → CORREÇÃO LOCAL → TESTE → POLÍTICA → ESCOPO → PROMOÇÃO → REUTILIZAÇÃO → TELEMETRIA → ROLLBACK se necessário.

2. POSIÇÃO NA ARQUITETURA

O Workspace NÃO substitui SOURCE_PROFILE, pipeline, QA, filas ou Supervisor.

SOURCE_PROFILE responde:
“COMO BUSCAR?”

WORKSPACE DE POLÍTICAS responde:
“QUANDO USAR, QUANDO NÃO USAR, QUAL FALLBACK ESCOLHER, QUAL LIMITE APLICAR E O QUE FAZER QUANDO FALHAR?”

Ele é uma camada de decisão acima dos perfis e abaixo das regras fixas do produto.


3. EXEMPLO REAL

Projeto Naruto
Domain = ANIME
Composition = ISOLATED

O app chama PokeAPI.

Isso é incompatível.

Sem Workspace:
o erro pode reaparecer em Naruto, One Piece, Bleach etc.

Com Workspace:
criar política:

scope:
DOMAIN=ANIME

condition:
source=PokeAPI AND universe != POKEMON

action:
BLOCK_SOURCE

Resultado:
PokeAPI nem entra na lista de candidatas para animes não Pokémon.

Para Pokémon:
a regra não se aplica.

5. HIERARQUIA DE ESCOPO

Toda política deve possuir escopo.

GLOBAL
→ DOMAIN
→ UNIVERSE
→ WORK_TYPE
→ COMPOSITION_CLASS
→ SEMANTIC_CLASS
→ PRESET
→ PROJECT
→ ITEM

Quanto mais específico, maior a precedência.

Precedência recomendada:
ITEM
> PROJECT
> PRESET
> SEMANTIC_CLASS
> COMPOSITION_CLASS
> WORK_TYPE
> UNIVERSE
> DOMAIN
> GLOBAL

Exemplo:
GLOBAL: Openverse prioridade 5
ANIME: Openverse prioridade 7
NARUTO: Openverse prioridade 9
NARUTO + ISOLATED: Openverse fallback

A regra mais específica vence.

6. CORE_RULE VS LEARNED_POLICY

CORE_RULE:
regra fixa, nunca alterada automaticamente.

Exemplos:
- não gerar imagem por IA sem autorização;
- não montar contextual;
- não aprovar preview;
- não reabrir FROZEN;
- não reduzir QA;
- não salvar imagem semanticamente errada.

LEARNED_POLICY:
regra operacional ajustável.

Exemplos:
- host X falha com WebP;
- PokeAPI não serve para Naruto;
- Fandom é melhor para isolados;
- timeout de fonte Y deve ser 4s;
- projetos >100 assets devem usar batch 20.

CORE_RULE sempre vence.

11. GAP SIGNATURE

O sistema deve gerar assinatura estável.

Exemplos:
SOURCE_INCOMPATIBLE|ANIME|POKEAPI
API_NOT_CONFIGURED|BRAVE
HTTP_403|HOST_X|ANIME
SEM_FONTES_ATIVAS|NARUTO|ISOLATED
QA_REJECT_WATERMARK|HOST_Y
TIMEOUT|TOOL=rejeitar_candidata
PRESET_TRANSPARENCY|CENTRAL_2

Se assinatura já existe:
occurrence_count += 1

Se não:
criar novo gap.


12. PROPOSTA AUTOMÁTICA DE POLÍTICA

O app pode criar PROPOSTA, mas não deve ativar regra global silenciosamente.

Exemplo:

GAP:
PokeAPI usada para Naruto.

PROPOSTA:
category=SOURCE_ROUTING
scope=DOMAIN:ANIME
condition=source:PokeAPI AND universe!=POKEMON
action=BLOCK_SOURCE
confidence=0.95
status=DRAFT

16. VERSIONAMENTO E ROLLBACK

Toda mudança cria nova versão.

Exemplo:

POL-001 v2 priority=8

Se v3 piorar:

Nunca apagar histórico.

18. EXEMPLOS DE POLÍTICAS

A) API SEM CREDENCIAL

GLOBAL:
api_key_required=true
AND api_key_configured=false
→ SKIP_SOURCE

Não gerar SOURCE_FAILURE.
Não escalar ao Supervisor.
Registrar SKIPPED_BY_POLICY.

B) POKEAPI

ANIME:
source=PokeAPI AND universe!=POKEMON
→ BLOCK_SOURCE.

C) FANDOM/WIKIA

ANIME + ISOLATED:
se discovery for necessário
→ usar discovery compatível + adapter;
→ se indisponível, Openverse;
→ não retornar SEM_FONTES_ATIVAS antes de tentar fallbacks válidos.

D) PROJETO GRANDE

project_items >= 100
→ qa_batch_size=20
→ relink_batch_size=20
→ parallelism=8
→ skip_waiting=true
→ delta_snapshot=true.

28. OUTROS GAPS INDUSTRIALIZÁVEIS

FONTES:
incompatibilidade, 403, 404, host lento, watermark, baixa aderência.

MATERIALIZAÇÃO:
formato problemático, redirect, preview falso, thumbnail, WebP.

QA:
composição, fundo, transparência, texto, watermark.

RELINK:
referência abstrata, query genérica, entidade inadequada.

PERFORMANCE:
ferramenta lenta, payload grande, timeout, N+1.

FILAS:
congestionamento, starvation, worker errado.

LEASE:
timeout, abandono, retomada.

ZIP:
nome duplicado, faltantes, manifesto.

PRESETS:
transparência, fundo, formato, resolução.

31. PERFORMANCE DO MOTOR DE POLÍTICAS

Não criar nova consulta MCP por item.

O backend deve resolver automaticamente.

Compilar políticas ativas em cache.

Cache key sugerida:
domain|universe|composition|preset

Invalidar cache somente quando política mudar.

Índices:
operational_policies(status, scope_level, domain)
operational_policies(universe, composition_class)
operational_policies(project_id, item_id)
operational_gaps(signature)
operational_gaps(status, occurrence_count)
operational_gaps(project_id, item_id)

32. POLÍTICAS DE ALTO IMPACTO

GLOBAL BLOCK
GLOBAL TIMEOUT
GLOBAL SOURCE PRIORITY
GLOBAL RETRY POLICY

Devem exigir aprovação explícita ou forte gate.

Mudanças locais, reversíveis e de baixo risco podem ser feitas pelo Supervisor automaticamente.


33. CONFIDENCE

0.00–0.49:
DRAFT

0.50–0.69:
TESTING

0.70–0.89:
ACTIVE local/universe

0.90+:
elegível para promoção, dependendo de telemetria.

Nunca promover para GLOBAL apenas por confidence.

34. AUTO-SUSPEND / AUTO-ROLLBACK

Se após ativação:
failure_rate sobe;
approval_rate cai;
tempo aumenta;
erros aumentam;

→ AUTO_SUSPENDED.

Supervisor analisa.
