CORVO LIBRARY V54 — HEARTBEAT, LEASE E RETOMADA AUTOMATICA
Data: 2026-08-27
Base: V53 — MCP baixo risco / uso continuo
Especificacao: BS14_HEARTBEAT_LEASE_RETOMADA_AUTOMATICA.txt

OBJETIVO
Evitar que uma execucao do ChatGPT/Supervisor que desapareca no meio do pipeline deixe o
projeto travado, sem manter um chat vivo, sem ping artificial e sem perder o estado persistido.

ARQUITETURA IMPLEMENTADA
CHATGPT assume projeto
→ Biblioteca adquire lease atomico
→ chamadas MCP reais renovam last_seen/expires
→ chat desaparece
→ lease vence
→ watchdog marca execucao ABANDONADA
→ pipeline vira PRONTO_PARA_RETOMADA
→ nova execucao chama assumir_proximo_trabalho_supervisor
→ adquire novo lease
→ reconcilia estado real
→ continua apenas os gaps.

As operacoes vinculadas ao projeto renovam automaticamente o lease quando recebem o
execution_id dono atual, incluindo:

- obter_candidatas_qa_visual

- continuar/pausar/cancelar processamento

- materializar_url quando o projeto pode ser resolvido
- materializar lote/fila quando o lote pertence ao projeto
- registrar QA por projeto e por lote vinculado
- adicionar candidatas / retry / correcao tecnica
- aprovar / rejeitar / relink / congelar
- alterar referencia/query/fonte/timeout de item
- reconciliar projeto
- gerar/regenerar/exportar ZIP vinculado
- consultas de coleta/materializacao vinculadas quando execution_id e informado.

Cada renovacao atualiza:

3. WATCHDOG
Nova funcao central:
- runSupervisorWatchdog()

Regra:
SE supervisor_status=ATIVO
E lease expirou
E projeto nao e terminal
ENTAO:
- execucao = ABANDONADA
- pipeline = PRONTO_PARA_RETOMADA
- motivo = LEASE_SUPERVISOR_EXPIRADO
- abandoned_at = agora
- registra eventos cronologicos.

O watchdog NAO:
- apaga R2;
- apaga candidatas;
- desfaz QA;
- cancela materializacoes deterministicas;
- reabre aprovados;
- reinicia o projeto.

4. WATCHDOG PERIODICO
worker/index.ts agora exporta handler `scheduled()` que chama o watchdog sem ChatGPT.
A cadencia configurada/recomendada e 2 minutos.

O pacote inclui docs/WATCHDOG_DEPLOYMENT_V54.txt.
O starter OpenAI Sites atual declara D1/R2 em `.openai/hosting.json` e explicitamente nao usa
wrangler.jsonc. Como nao ha neste checkout um campo documentado de cron do Sites, o pacote nao
inventa configuracao de deploy. Para execucao estritamente a cada 2 minutos sem trafego, o
runtime deve anexar o Scheduled/Cron Trigger ao Worker. Mesmo sem ele, o watchdog roda antes de
assumir novo trabalho e ao consultar o estado, portanto lease vencido nunca bloqueia uma futura
retomada.

5. AQUISICAO ATOMICA / COMPARE-AND-SET
Nova ferramenta MCP:
- assumir_proximo_trabalho_supervisor

Ela:
1. executa watchdog;
2. localiza projeto elegivel priorizando PRONTO_PARA_RETOMADA, QA, relink e materializacao;
3. ignora projeto com lease valido de outra execucao;
4. adquire lease por UPDATE condicional atomico no D1;
5. cria/atualiza supervisor_executions;
6. reconcilia o projeto;
7. registra PROJECT_RECONCILED;
8. retorna execution_id, lease_expires_at, next_action e pending_items.

Dois Supervisores nao conseguem adquirir simultaneamente o mesmo projeto.

6. BLOQUEIO DE EXECUCAO ANTIGA
Escritas MCP vinculadas a projeto exigem o execution_id atual depois que o Supervisor assume.

Se A perdeu o lease e B assumiu:
- leitura de A pode continuar;
- mutacao de A recebe SUPERVISOR_REPLACED ou LEASE_NOT_OWNED;
- A nao recupera o controle automaticamente.

7. RECONCILIACAO ANTES DA RETOMADA
A ferramenta de assumir executa reconcileAutomaticProject() depois de adquirir o lease e antes
de devolver o trabalho ao Supervisor.

- PARA_ANALISE/PARA_QA_VISUAL;
- aprovados/congelados;
- gaps/relink;
- ZIP existente;
- fila de decisoes.

OBSERVACAO DE DEPLOY
Para cumprir literalmente "rodar a cada 2 minutos sem nenhuma requisicao", o runtime publicado
precisa associar o Scheduled Trigger de 2 minutos ao handler `worker.scheduled`. A logica,
handler e configuracao persistente estao dentro da V54; o checkout de OpenAI Sites fornecido nao
expoe uma chave documentada de cron em `.openai/hosting.json`, portanto a V54 nao adiciona uma
configuracao de hosting inventada.

RESULTADO
O estado operacional necessario para retomada fica integralmente na Biblioteca. Uma nova
execucao nao precisa ler a conversa anterior, receber handoff manual nem perguntar ao usuario se
pode continuar.
